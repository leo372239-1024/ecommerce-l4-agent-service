## 0. 排序逻辑（先看这条）

**不是按「数字最大」排序，而是按三个维度综合：稀缺度 × 面试可深挖轮次 × 与 Agent 岗相关度。**

一条判断准则：如果一个亮点撑不住 2 个追问轮次，数字再漂亮也不能排前面；反过来，没有大数字但能撑 20 分钟深挖的机制设计，应该放第一。

| 序号 | 亮点 | 梯队 | 可深挖轮次 | 稀缺度 |
|---|---|---|---|---|
| 1 | 写路径幂等与回执对账（超时 ≠ 回滚） | 🔴 | 5+ | 极高 |
| 2 | 权限优先 + 读写分离的工具准入 | 🔴 | 4~5 | 极高 |
| 3 | 可验证计划（TaskSpec + 校验 DAG）+ 消融证据 | 🔴 | 4 | 高 |
| 4 | 时效记忆：历史不构成当前事实与授权 | 🟠 | 3~4 | 中高 |
| 5 | 可恢复执行与长流程稳定性 | 🟠 | 3 | 中 |
| 6 | 评测方法论与诚实披露 | 🟢 | 2~3 | 中（信任倍增器） |
| 7 | 全栈交付与可观测性 | 🟢 | 1~2 | 低（入场券） |

## 1. 🔴 第一梯队：决定面试走向的差异化亮点

### 第 1 位｜写路径的幂等与回执对账（「超时 ≠ 回滚」）

**为什么最吸引面试官。** 绝大多数 Agent 项目停在「能调用工具」；这里回答的是「调用之后结果不确定怎么办」——这是 Agent 落地生产时真正的死穴。一句话可以勾出后端面试的全部核心考点：幂等键设计、唯一约束 vs 缓存键、合法状态迁移、Outbox/Inbox、receipt 对账、租约与 fencing。

**核心机制**

- 写操作先生成绑定当前状态版本、金额和作用域的提案；客户确认与必要的主管审批**独立记录**。
- 执行前重新读取事实，状态变化会让**旧提案失效**，旧审批不继承。
- 事务携带稳定 `operation_id` + 参数 hash + PostgreSQL 唯一约束 + 业务状态机。
- 发送后响应丢失时，**先按 operation receipt 查询并对账**，不重放非幂等 POST；无法确认则转人工。
- `checkpoint` 不能单独保证外部副作用 Exactly-Once。

**证据**

| 指标 | 结果 |
|---|---|
| 失败恢复主集 | P 144/144（100%）vs A-reflect 48/144（33.33%） |
| family 均衡差 | +66.67pp，95% 聚类 bootstrap CI **[+33.33, +100]pp** |
| 控制组（未混入主分母） | 永久故障停止两组均 24/24 PARTIAL；无故障对照两组均 6/6 SUCCEEDED |
| 额外验收 | 「写后丢响应」业务故障注入通过 |

**候选人口径**

> 我把非幂等 POST 的重放路径从代码里删掉了——超时后先查 operation receipt 再决定；HTTP 失败不能证明数据库事务回滚。

**面试可能的追问**

- 幂等键怎么设计的？为什么缓存键不能单独证明财务写入唯一？
- Outbox 通知丢了怎么办？（答：Worker 还能轮询数据库 Outbox，Redis 不是唯一任务来源）
- 回执查询本身超时呢？（答：有限重试，仍无法确认则转人工，不做二次扣款）

### 第 2 位｜权限优先 + 读写分离的工具准入（把安全从提示词下沉到架构）

**为什么。** 它把「工具调用准确性」这个热门话题从「调参」提升到「架构约束」，面试官会立刻判断你是在做系统而不是在写 prompt。配套还有一个完整的**真实 bug 故事**。

**核心机制**

1. `Router.allowed()` 先复核身份、角色、订单归属、商家归属，产出工具级 allowlist。
2. BM25 检索与向量检索**都以该 allowlist 作为过滤条件**（ES `terms.tool_id` / pgvector `tool_id=ANY(:ids)`）。
3. `projection_candidates()` 只保留 `risk == "read"`；3 个写工具（`create_return` / `submit_refund` / `cancel_order`）**永远不参与相似度检索**，只能由绑定提案的执行路径触发。
4. 四段漏斗：双路各召回 30 → RRF Top20（k=60）→ qwen3 精排 Top6 → 模型在 6 个授权候选内选 1 或调 `clarify`。
5. 参数级接地校验：工具名必须在候选集内、Pydantic 参数校验、`order_id` 必须严格等于服务端绑定值、`operation_id` 必须逐字出现在原文。

**真实 bug 故事（面试高价值）**

> MCP SDK 运行时参数校验缺口：工具 advertised JSON Schema 声明 `additionalProperties=false`，但 SDK 注册工具时使用的运行时参数模型没有同步该约束。边界探针发现 **37 个只读工具会静默接受多余的 `tenant_id`**。修复为注册时强制 `strict + extra=forbid` 并 rebuild，40 工具 × 5 类参数注入探针全部被拒绝。
> 教训：契约声明与运行时强制是两件事，安全边界必须落在运行时。

**证据与硬约束**

| 项 | 结果 |
|---|---|
| 1000 项目录（40 真实工具 + 960 干扰描述），50 例 × 3 trial × 2 组 | 本项目 150/150，基线 R-hybrid 150/150，**差值 0pp** |
| 200 项目录 | 两组均 150/150 |
| 50 项目录 | 本项目 149/150，基线 150/150（本项目略低一次） |
| 成本与延迟（1000 目录） | 本项目 283,246 Token / 中位 4.10s；基线 191,260 Token / 3.37s（**本项目更差**） |
| 参数注入探针 | 修复后 40 × 5 全部被拒 |

> ⚠️ **不能说「路由更准」。** 基线已到样本上限，实验只能证明「候选池放大 25 倍未退化」。

**钩子**

> 写工具在架构上不可被相似度检索命中——不是靠 system prompt 说不要乱写，而是模型根本拿不到入口。

### 第 3 位｜可验证计划（TaskSpec + 校验 DAG + 投影覆盖检查）

**为什么。** 这是项目**唯一有统计支持的 headline 方法论**，而且通过消融实验把「机制」和「增益」分离开了——这套「证明是我的机制在起作用」的方法论，是区分「调参党」与「做研究的人」的分水岭。

**核心机制**

- 模型只提交有原文实体证据且覆盖每订单目标范围的 Pydantic TaskSpec。
- 程序编译强依赖 DAG，节点、依赖、读写顺序、绑定实体、预算均可验证。
- v6 增加**已发布投影的覆盖检查**：原文已识别的属性若在解析查询中遗漏，拒绝该计划并进入有限修复（`requested_projection_omitted`），避免只完成复合请求的一部分就报告成功。
- 订单号 token 边界匹配，防止 `ORD-100` 误配 `ORD-1000`（`ungrounded_order_id`）。
- 否定表达（不是/不要/无需）保留语义路径，不用关键词硬猜。

**证据**

| 比较组 | 基线 | P | family 均衡差 / 95% CI | 结论 |
|---|---:|---:|---|---|
| 主集 P vs B2（原生 ReAct + BM25/dense/RRF/rerank） | 117/180 | 159/180（88.33%） | +9.14pp / **[−4.66, +23.45]pp** | 点目标达到，**区间含 0，未获支持**；P 未达预登记 ≥90% |
| 消融 P vs A-plan（关闭类型化计划） | 139/180 | 159/180 | **+8.56pp / [+1.03, +17.59]pp** | **区间不含 0，获支持** |

> 主动讲出「主指标 CI 含 0、未达 ≥90% 门槛」，比只讲 +9.14pp 更能建立信任。

## 2. 🟠 第二梯队：强加分项

### 第 4 位｜时效记忆与上下文预算：历史不构成当前事实与授权

**数字最漂亮，但叙事重心不在数字。** 两条理由：①「记忆」是被讲烂的热词，面试官默认你在跟弱基线比；② 真正的差异化是**旧金额、旧业务状态、历史审批不继承、不能作为当前事实或授权**这个安全语义。百分比只是脚注。

**核心机制**

- 拥有者隔离的会话实体账本用于**指代解析**，但不授予权限、不作为当前事实来源。
- 时间/作用域/引用卸载纳入 Token 预算；执行前重新读取商家系统。
- 旧金额、业务状态、历史审批不成为当前事实或授权。
- 当前任务位于历史引用之后，避免旧请求替代当前目标。
- 会话删除停止召回；任务审计按独立保留政策继续存在。

**证据**

| 项 | 结果 |
|---|---|
| 时效记忆主集 | P 180/180（100%）vs M-vector 62/180 |
| M-vector 成功率（两套口径不可混用） | 任务级 **34.44%**（62/180，每单元等权）；**family 均衡率 24.36%**（13 个 family 等权平均） |
| family 均衡差 | **+75.64pp** = 100% − 24.36%，95% CI **[+55.13, +92.31]pp** |
| 条件 Token（62 对两组都正确且 usage 完整） | 513,308 → 180,291，**−64.88%** |
| 另 24 个已知承运遗漏回归（不进主集） | P 12/12，M-vector 9/12（单列披露） |

**必答边界**

- **两个成功率口径不可互推**：任务级 34.44% ≠ 均衡率 24.36%，故 `100% − 34.44% = 65.56pp` **不是** family 均衡差。差异来自 `explicit_control` 一族有 36 个单元（其他族各 12 个），在任务级口径里占 20% 权重且基线 100% 全对，把基线从真实的 18.06% 抬到 34.44%；均衡口径下该族只占 1/13。被追问时先讲这一句，再报 75.64pp。
- 条件 Token 仅覆盖主集的 **34.44%**（62 对两组都正确的配对；因 P 全对，「两组都对」与「M-vector 正确」是同一集合，故该比例与任务级成功率同值同源，**不可当作两个独立证据**），不代表全量任务成本，**不含离线 embedding**。
- M-vector 基线含 2004 次离线历史检索请求（P 为 0），离线费用需另行对账。
- 无独立人工盲审，属探索性证据。

### 第 5 位｜可恢复执行与长流程稳定性

**为什么。** LangGraph checkpoint + 租约/fencing + 持久 AG-UI 事件与游标续传 + Outbox 通知丢失去 DB 轮询兜底，分布式信号很硬，且有长时验收背书。

**证据**

| 项 | 结果 |
|---|---|
| 2 小时连续运行 | 实测 7200.015s；120/120 只读通过、**0 失败**；123 次模型调用、298,160 Token；资源采样 223 点 |
| 资源峰值 | 项目普通服务容器峰值 **2.235 GiB**；结束时重启数 0、OOM=false |
| 同宿主 Worker 接管 | 停止后约 **30.19s 被接管**，fencing 1→2，28 条事件连续 |
| Docker API 控制负载 | 50 并发 × 600s：158.75 RPS、P95 ≈563ms（相对 10 并发吞吐 −9%、P95 ×7.1） |

**必答边界**

- 同宿主进程接管 **≠** 跨故障域 HA；数据库、Redis、MCP 与入口仍为单实例。
- 峰值不含 benchmark 容器、Windows/WSL 与其他项目。
- API 控制负载不触发 LLM，**不代表 Agent 对话吞吐**；100 并发触发预登记延迟停止条件，不记为通过。

## 3. 🟢 第三梯队：基础项（无差异化，但没有会减分）

### 第 6 位｜评测方法论与诚实披露 —— 当「信任倍增器」用，别当亮点讲

**内容**：预登记协议、family 均衡率、family 配对聚类 bootstrap（4000 次、seed 10001）、3762 个 schedule 单元、失败批次与旧供应商结果原样保留、路由组件指标与真实业务指标分开、V3 不与 V4 合并。

**为什么排这里**：单独讲不抢眼，但**性价比极高**——面试官一旦问「这个数字怎么来的」，能答出这一套，前面所有数字的可信度都会被上调。建议花 2 句话埋在量化结果后面，不单独占 bullet。

**同时也是真实留痕**：V3/V6 的监控披露（进度检查读到含 `strict_success` 的日志行）均如实保存。

---

### 第 7 位｜全栈交付与可观测性 —— 入场券，不是亮点

React / Antd 三工作台（客户 / 客服 / 主管）+ FastAPI（async、OpenAPI）+ 独立 Worker / 商家 MCP / Sandbox 进程 + Docker Compose（镜像 digest 与锁文件冻结）+ OTel → Jaeger、Prometheus → Grafana。

| 项 | 结果 |
|---|---|
| 后端测试 | Windows 与 Docker Linux 各 **293 项**通过（21.23s / 6.24s） |
| 前端 | SSE 5 项测试 + TypeScript 构建通过 |
| 业务验收 | V6 镜像 9 项检查、8 次真实模型任务 |
| 测试 OIDC / 本地账户 | 协议验证通过，**不等于已接入组织 IdP** |

## 5. 简历 bullet 模板（按排序取用，建议 4~6 条）

1. （第 1 位）设计并实现**写路径的幂等事务边界**：稳定 operation ID + 参数 hash + PostgreSQL 唯一约束 + 合法状态迁移 + 回执对账；响应丢失时先查 operation receipt 再决定，不重放非幂等请求。冻结故障集严格成功 144/144，对照关闭证据反思基线 48/144。
2. （第 2 位）设计**权限优先、读写分离的 MCP 工具路由**：身份/角色/订单归属/商家归属在检索前硬过滤，写工具不参与相似度检索、仅由绑定提案的执行路径触发；四段召回漏斗将候选从 1000 压到 6，模型仅在授权候选内有限选择。定位并修复 MCP SDK 运行时参数校验缺口（37 个只读工具曾静默接受多余参数）。
3. （第 3 位）构建**可验证计划机制**：Pydantic TaskSpec + 编译期校验 DAG + 已发布投影覆盖检查。消融实验支持其对复杂任务成功率的正向效应（159/180 vs 139/180，family 均衡差 +8.56pp，95% 聚类 bootstrap CI [+1.03, +17.59]pp）。
4. （第 4 位）实现**拥有者隔离的四层记忆与上下文预算**：实体账本用于指代解析但不授予权限，旧金额/旧状态/历史审批不继承。时效记忆主集 180/180 vs 向量历史基线 62/180（任务级 34.44%；**family 均衡率 24.36%**，family 均衡差 **+75.64pp**，95% CI [+55.13, +92.31]pp）；条件 Token 下降 64.88%。
5. （第 5 位）基于 LangGraph + PostgreSQL checkpoint 实现**持久可恢复执行**：租约、fencing 与持久 AG-UI 事件游标支撑断线续传与进程接管；完成 2 小时 Docker 连续运行验收（120/120 通过、0 失败），同宿主 Worker 接管约 30.19s。
6. （第 6/7 位，合一条）Docker Compose 交付 React 工作台 / FastAPI / Worker / MCP / Sandbox 与 Elasticsearch BM25 + pgvector + RRF + 精排检索栈，接入 OpenTelemetry / Prometheus / Grafana / Jaeger；后端 293 项测试在 Windows 与 Docker Linux 均通过。

## 6. 写作红线（写简历时必须同时披露）

| 项 | 必须披露的内容 |
|---|---|
| 规划主指标 | family 均衡差 CI 含 0，正效应**未获支持**；仅消融 A-plan 获支持；P 未达预登记 ≥90% |

| 记忆 / 恢复 | 无独立人工盲审；结果为冻结模拟场景，不可外推真实商家或任意攻击 |
| 可用性 | 单宿主部署，同宿主接管 ≠ 跨故障域 HA；未交付 K8s / Istio / Kafka |
| 费用与 Token | 网关报告值不是账单；记忆 Token 条件比较不含离线 embedding；provider mix 两组不同 |
| 能力边界 | 知识库仅 TXT/Markdown（实际约 4MB 文本）；任意代码执行关闭；组织 IdP / 生产 TLS / 异地备份未验收 |
