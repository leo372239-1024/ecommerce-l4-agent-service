## 2. 项目概述（2 行，放在 bullet 之前）

面向电商售后的单 Agent 系统，覆盖「理解任务 → 计划 → 事实核验 → 提案 → 客户确认/主管审批 → 事务执行 → 回执 → 人工工单」闭环。设计重点不在「能对话」，而在**把 Agent 的高风险动作变成可验证、可审计、可恢复、且不可被诱导的事务**。

## 3. 六条 bullet 成稿

### ① 写路径幂等与回执对账（🔴 首条，决定面试走向）

> 设计并实现**写路径的幂等事务边界**：稳定 operation ID + 参数 hash + PostgreSQL 唯一约束 + 合法状态迁移，响应丢失时先查 operation receipt 对账再决定，不重放非幂等请求；冻结故障集严格成功 144/144，关闭证据反思的对照基线 48/144（family 均衡差 +66.67pp，95% 聚类 bootstrap CI [+33.33, +100]pp）。

### ② 权限优先 + 读写分离的工具准入

> 设计**权限优先、读写分离的 MCP 工具路由**：身份、角色、订单归属、商家归属在检索前作为硬过滤条件注入 BM25 与向量两条通道，写工具不参与相似度检索、仅由绑定提案的执行路径触发；四段漏斗把候选从 1000 压到 6，模型只在授权候选内选择。定位并修复 MCP SDK 运行时参数校验缺口（37 个只读工具曾静默接受多余参数），修复后 40 工具 × 5 类参数注入探针全部被拒。

### ③ 可验证计划（🔴 本项目唯一有统计支持的 headline 方法论）

> 构建**可验证计划机制**，把「计划」从模型输出改为程序编译产物：模型仅提交带原文实体证据的 Pydantic TaskSpec（订单范围、逐单目标绑定、查询属性，禁止改写或补造实体），由 `compile_plan()` 生成强依赖 DAG，编译期校验拓扑无环、节点身份、强制依赖表、所有权守卫与读写标记，并新增已发布投影覆盖检查，避免只完成复合请求的一部分就报告成功。消融实验（仅把编译 DAG 换为模型线性步骤，其余能力保留）支持该机制对复杂任务成功率的正向效应：159/180 vs 139/180，family 均衡差 **+8.56pp**，95% 聚类 bootstrap CI **[+1.03, +17.59]pp**。全部口径与目标值在推理前冻结。

### ④ 时效记忆与上下文预算

> 实现**拥有者隔离的四层记忆与上下文预算**：实体账本仅用于指代解析、不授予权限，旧金额、旧业务状态与历史审批不继承为当前事实或授权，执行前重新读取商家系统。时效记忆主集 180/180，向量历史基线 62/180（family 均衡率 24.36%，family 均衡差 **+75.64pp**，95% CI [+55.13, +92.31]pp）；条件 prompt token 下降 64.88%。

### ⑤ 可恢复执行与长流程稳定性

> 基于 LangGraph + PostgreSQL checkpoint 实现**持久可恢复执行**：租约、fencing 与持久事件游标支撑断线续传与进程接管；完成 2 小时 Docker 连续运行验收（7200.015s、120/120 只读通过、0 失败），同宿主 Worker 接管约 30.19s。

### ⑥ 全栈交付与可观测性（写 1 行即可，别展开）

> 以 Docker Compose 交付 React 三工作台 / FastAPI / Worker / 商家 MCP / Sandbox，检索栈为 Elasticsearch BM25 + pgvector + RRF + 精排；接入 OpenTelemetry / Prometheus / Grafana / Jaeger，后端 293 项测试在 Windows 与 Docker Linux 均通过。

**B. 标准版（即 §3 第 ③ 条，推荐）**

**C. 强化版（投递 Agent 算法 / 研究向岗位时加这一句）**

> 主集与强检索 ReAct 基线对比为 +9.14pp，但 95% CI [−4.66, +23.45]pp 含 0，因此**不主张「整体优于 ReAct」**，结论只挂在消融对照上。

## 5. 禁用表述（写了就是追问或背调风险）

| ❌ 不能写 | 原因 |
|---|---|
| 「提升 23.33pp」/「高出 23.33pp」 | 这是**微平均（任务级）**口径且**没有配套区间**，只是描述性数字，不能与 family 均衡差混用或互推 |
| 「相比 ReAct 提升 9.14pp，效果显著」 | 主指标 95% CI 含 0，正效应**未获支持** |
| 「成功率 88.33%，显著优于基线」 | 同上；且未达预登记 ≥90% 绝对质量门槛 |
| 「工具路由准确率提升 X%」 | 基线已触顶（两组均 150/150，差 0pp）；只能写「候选池放大 25 倍未退化」 |
| 「提升了工具调用准确率」 | 路由实验是组件级实验，不等于真实业务准确率 |
| 「已接入真实商家 / 可用于生产」 | 结果为冻结模拟场景，**无独立人工盲审**，不可外推 |
| 「实现跨故障域高可用」 | 仅同宿主进程接管，DB / Redis / MCP / 入口均为单实例 |
| 「准确率 / 效果行业领先」 | 未对封闭商业系统做同集测试 |

## 6. 写完必须能答的追问

| 追问 | 一句话答法 |
|---|---|
| 主集和消融，哪个能支持你的结论？ | 只有消融 A-plan，其 CI 不含 0；主集与 B2 的 CI 含 0 |
| 为什么用 family 均衡而不是任务级成功率？ | 同一场景的 5 次 trial 不独立，naive 区间会偏窄 2~3 倍，故先族内平均、再对族做配对聚类 bootstrap |
| 那为什么还要报 88.33%？ | 它是预登记时约定「另列」的描述性指标，回答部署视角；不配区间、不用于推断 |
| 是机制起作用，还是 prompt 变好了？ | A-plan 保留 TaskSpec 作为 prompt 输入，仅关掉编译与校验，变量锁定在单一机制 |
| 为什么不让模型自己给依赖关系？ | 让模型给依赖，等于把可验证性交给被验证对象；顺序与权限必须由服务端决定 |
| 这个机制解决的是什么真实问题？ | 写操作场景：ReAct 可以在最后一轮用自然语言声称已处理，而写节点存在与否由编译期校验决定，运行时绕不过去 |
| 消融的优势集中在哪？ | 全部来自 5 个写操作族（60/180 单元）；纯读场景基线反超，这点被主动披露 |
