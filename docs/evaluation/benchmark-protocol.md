# Docker 真实评测、基线与成果验收协议

日期：2026-10-09；步骤9探索性执行登记见[本轮登记](step9-preregistration.md)，实际结果与缺口见[交付审查](../delivery/step9-benchmark-review.md)。本协议的80/200条独立盲测、大目录与上线门槛数字仍是**样本/预算/目标设计**，不是实测成绩。本轮60条EC自动案例不替代完整协议要求。与[技术复审](../research/2026-10-09-agent-core-review.md)、[核心设计](../architecture/agent-core-v2.md)联合使用。

## 1. 什么可以作为项目成果

成果必须同时提供：业务问题、一般工程基线、改进机制、同条件实测、样本与置信区间、成本/延迟/人工介入和安全代价、可复现配置与原始轨迹。至少 3 项深化在其预注册主指标上显示明确优势。只能说在指定中文电商测试集、模型、工具目录与资源环境内优于具体基线；没有直接实测不能称超越 Salesforce Agentforce 或 Dify。

项目“生产质量”的证据分三层，互不替代：

1. 功能质量：真实模型 + 真工具执行 + 可重置业务数据库 + 动态用户/环境，评分读取最终业务状态。
2. 工程可靠性：真实 Docker 服务，故障注入、幂等、权限隔离、审批准入、重启恢复、备份/恢复。
3. 性能容量：API/事件/队列用受控模型桩确定架构上限；真模型另测实际限流与端到端吞吐。不以桩的 RPS 宣称真实 Agent RPS。

## 2. 数据集、分割与质量审查

最低交付：≥50 条**可执行、人工审查的黄金案例**。本轮已提供 [80 条用例规格](golden-case-catalog.md)，这是候选测试规格，尚不是已生成 fixture 和自动 oracle 的正式黄金集。最终建议 20–40 条开发案例 + 80 条独立盲测案例起步，正式比较扩展到约 200 条盲测案例；样本不足以证明目标时增加独立场景，而非把同例重试当独立新样本。

按任务/模板/订单实体族分割；同一模板的小改字不能同时进入训练/开发与盲测。每条保存 ID、scenario family、难度、种子、fixture、用户初始任务与后续允许回复、政策版本、工具目录版本、事件注入时间/触发点、必需完成条件、禁止副作用、允许澄清/人工条件与 oracle。来自 τ retail 的案例需保留原许可与 provenance，中文本地化后重新核验，不把公共题目视为完全未知数据。

覆盖：售前/知识、身份与多轮、订单/物流、退款退换、复合任务、工具消歧与规模、长会话/记忆、故障/恢复、授权/注入、审批/人工闭环。必须包含无匹配工具、不可执行任务、用户撤销、权限撤销、状态变化、未知写结果、多个合法执行顺序；只测 happy path 不合格。

黄金答案是**终态约束与可允许的业务轨迹集合**，不是一条唯一工具序列。schema/金额/归属/必需核验/审批/副作用可用程序判定；沟通完整性由人工定义 rubric。测试作者按 fixture 独立复算政策和金额，另人审查或用户审查困难样本。发现题目矛盾时登记 errata，所有变体使用同一修订版重测，不能只为改进组修题。

AWM 与记忆只从开发集学习；评测冻结技能、索引与 memory snapshot。每个 episode 使用独立业务快照和 scope；跨会话记忆任务明确初始化同一用户历史，不允许前一测试题答案泄漏下一题。评测 oracle 数据库/隐藏答案与 agent 网络隔离，Agent-as-Judge 仅有评分所需只读工具。

## 3. 对照组与消融组

| 组 | 定义 | 用途 |
|---|---|---|
| B0 | 普通 LangGraph ReAct，完整工具 schema（窗口内），标准 schema 校验、固定上限、窗口/摘要；同样的底层授权/业务幂等/审批 | 可解释的一般实现基线；大目录超窗口需记为不可支持而非暗中裁掉难工具 |
| B1 | 较强常规实现：ReAct + 权限过滤 + dense Top-K 工具检索 + 普通历史摘要/向量记忆 + 固定重试 | **主要比较基线**，避免只挑弱基线得出优势 |
| P | 完整改进 Harness，同模型、业务工具、政策与执行预算 | 项目组 |
| A-plan | P 去掉类型 DAG/业务骨架/增量计划校验，其他保持 | 分离复杂规划贡献 |
| A-route | P 将混合/精排/契约排序替换为 B1 dense 策略；底层授权不变 | 分离工具路由贡献 |
| A-memory | P 改普通窗口/摘要与 B1 长期记忆，关闭 AWM/时效门控/证据摘要；仍保留业务账本 | 分离记忆与上下文贡献 |
| A-reflect | P 关闭外部反馈驱动计划修复/无进展策略，使用相同上限的文本自检/固定重试；底层幂等不变 | 分离反思与恢复贡献 |

每个分层实验只改变一项，初始超参数在开发集锁定。P 先与 B1 比，再报告 B0；有收益但消融无差异时不能把收益归因于该模块。另测规划-only/路由-only/AWM-only/遮蔽-only/摘要-only等成本较小的 microbenchmark，查明交互作用。不要为了让恢复组显著而关闭基线的业务安全控制。

可选真实 Dify 对照：相同模型、同工具 REST/MCP、同知识版本、同确认/审批政策，公布实现配置、release/commit、限制和同等调参预算。若配置不可等价，按功能差异列明，不当严格架构对比。Agentforce 当前无授权可部署环境，不制作数字排名。

## 4. 控制变量与重现

冻结 Git commit、镜像 digest、Python/npm lock hash、Compose profile、OS/Docker版本、CPU/RAM限制、模型请求名与返回名/版本、采样参数、预算、prompt/schema/skill/policy/catalog hashes、embedding/reranker revision、评测器 commit、用户模拟器版本及独立种子。

同模型固定温度/采样参数（仅使用实际 API 支持字段）；设 seed 也不能假定服务端完全确定。相同场景、用户偏好与外部事件日程配对；互动模拟器可根据 Agent 行为产生不同合理回复，不能强迫所有轨迹相同。固定脚本用户与动态模拟用户分别报告；模拟器不接触 oracle、不提供神谕提示。对用户模拟器失败单独计数并按预定规则重跑所有对应组。

各变体随机交错运行，避免模型供应商时段漂移；记录限流/超时/失败，缓存明确关闭或独立冷/热阶段。共享硬件一次运行一组压力任务，embedding 索引相同预热；费用同时包含规划/反思/摘要/检索推理/用户模拟/Judge，项目 Agent 主成本与评测支出分账。

所有任务使用真正工具执行；“模型返回已成功”不是完成。离线录制轨迹可用于回归，但不能冒充本轮真实推理测评。Mock 业务 API 是本项目接受的业务边界，报告注明非商户生产账务。

## 5. 指标定义

| 指标 | 定义与统计口径 |
|---|---|
| Strict task success | 所有必需终态、政策条件、确认/审批与禁止副作用检查均通过；报告按任务类别/难度分层 |
| Complex task success | 多实体、条件替代、用户变化或 ≥5 有依赖步骤的预先标注子集严格成功率 |
| pass^k | 同任务 k 次均成功的一致性指标；有 n 次、s 次成功时用 C(s,k)/C(n,k) 的估计后按任务平均。不是“k 次至少一次成功” |
| Goal/mandatory-step coverage | 需求目标完成比例、漏必需条件数；部分完成单独计分，不能替代 strict success |
| Tool Recall@K | 在该决策点的合法必要工具集合中，候选是否包含至少一条允许路径所需工具；多工具目标另报集合覆盖 |
| Tool/argument joint accuracy | 首次选择属于合法工具集合且必需参数语义正确；schema合法、修复后准确率、缺参澄清率另报 |
| Unnecessary-call rate | 没有提供任务有用信息/副作用且非必要校验的调用占比；合理确认读取不当作浪费 |
| Evidence correctness | 金额/状态/政策/库存等关键 claim 与当时权威证据一致，citation 指向正确授权证据 |
| Recovery success | 注入故障后满足原任务或预定义合法交接条件且无禁止副作用的比例；意外 HANDOFF 不算自动完成 |
| Memory correctness | 记忆题的时间更新、用户纠正、实体归属、删除、来源引用正确；不把检索相似度当准确率 |
| Safety | 越权/注入/数据外泄/重复或错误副作用各自成功攻击率，同时报告 benign false refusal |
| Autonomous resolution | 预先标注允许自动完成的任务中，无非必要人工介入且 strict success；所有任务总体安全闭环率另报 |
| 成本与性能 | 每任务输入/输出Token、模型/工具次数、金额/耗时；首个有用状态事件、首个有用回答、最终完成 P50/P95/P99；队列/执行/人工等待分开 |

Judge 分三层：确定性程序 → 带只读验证工具的证据 Judge → 人工裁决。不同模型 Judge 仅在实际可用时使用；同模型自评不得单独裁定质量。硬性违规即失败，不能被高文风分抵消。Judge prompt 要限制工具/防答案注入，盲化变体名称；人工双评困难/争议样本与随机抽样，记录分歧及裁决依据。若没有第二模型费用/凭据，使用程序+人工，不用“独立 Judge”名义调用同模型掩盖相关性。

## 6. 主实验与统计

分阶段运行：

- 管线冒烟：10 条开发案例，确认 fixture/oracle/归档正确；只验证管线不作为成果。
- 先导：20–40 条开发案例，调 K、预算、阈值、压缩参数；不在盲测集调参。
- 盲测起步：80 条 ×5 trial，每变体 400 个 episode；B0/B1/P 与主要消融分批执行。必要时扩展到 200 条或更多独立场景。预先估算工具/模型调用上限与供应商限额后制定日程。
- 工具规模 microbenchmark：50/200/1000 目录，每档 ≥200 个独立决策点，包含近义、缺参、无匹配、版本、跨域干扰；参数与召回标注人工复核。
- 专项故障与攻击：至少 200 条可区分故障/安全案例（或注入场景），正常输入另配对；其中不相互独立的变体按 family 聚类，不把批量改字视为样本量增长。

对 P−B1 的任务成功/恢复/记忆提升以任务/场景 family 为抽样单位做 paired bootstrap 95% CI；不得把同一个 task 的 5 次运行当独立任务。单比例报告 Wilson 区间，必要时对首次配对二元结果做 McNemar。成本采用配对相对变化与 CI，延迟报告分布而非只有均值。四项预注册主比较使用 Holm 校正或明确标为探索结果，不能挑显著结果隐藏其他实验。

目标值见调研文件：规划 +8pp、路由 +5pp、长会话 +8pp/Token −25%、恢复 +15pp 等。达标还需 CI 支持正确方向，安全/非目标质量无实质劣化；等价/非劣目标须提前定义 margin 并采用对应检验，不能用“差异不显著”声称同等。80 条不足以确认很小差异时扩大独立样本或报告 inconclusive。

严格上线门槛提案：黄金集整体 strict success ≥90%，复杂子集 ≥85%，人工必要任务正确接管 ≥95%，关键金额/归属/授权/审批/重复副作用在冻结回归中无失败；工具 Recall@K ≥98%、联合首次正确率 ≥95%为专项目标。**这些是 MVP 验收目标，不是行业顶尖已达成，也不是百分之百安全证明。** 达不到时如实报告并继续修复或重新审查模型能力。

零失败样本应写 `0/N`。独立同分布假设下零观察的单侧 95% 上界约为 `3/N`，3000 次才约 0.1%；真实攻击可自适应且相关，不能用这个计算宣称注入风险普遍低于阈值。

## 7. Docker 部署与工程负载评测

部署清单通过后再跑基准；报告完整实际资源、profile 与依赖。已有 MySQL/MinIO/KnowDesk volumes 保持隔离，使用本项目新命名卷和不冲突端口。数据库/缓存/ES端口默认 loopback 或不暴露，公网仅经过代理与认证。

必须真实验证：容器构建（锁文件失败不能 fallback）、迁移、服务 ready 与 live 区分、PG/Redis 断开健康降级、MCP 链路、真实模型 capability probes、可用 trace/指标、日志脱敏、SSE 回放与审批重启恢复。

性能场景与初始负载：

| 场景 | 负载递增 | 必看结果 |
|---|---|---|
| 控制 API（模型桩） | 1/10/50/100 并发，热身后 10–15 分钟稳定区间 | RPS、P95/P99、错误/429、DB池、CPU/RAM、Outbox lag |
| SSE 流 | 10/50/100/200 连接，含慢客户端、重连、游标过期 | 内存增长、事件延迟、seq/gap、回放缺失与隔离 |
| Worker/工具 | 1/2/4 Worker，只读并发与同实体写冲突 | 租约公平、背压、超时、重复消息、fencing拒绝、业务唯一性 |
| 真模型端到端 | 从 1/2/4 并发开始，遵守账号实际 RPM/TPM | 限流占比、队列时间、吞吐、任务完成、真实成本 |
| Soak/故障 | 最少 2 小时持续任务；OOM/kill/API或Worker重启/Redis与PG重连 | 泄漏、任务丢失、未知账务操作、正确恢复与积压清理 |

低资源单机未必支持最高档；逐档停止于预定义错误/资源阈值，失败档也写入报告。资源压力与供应商限流分开归因。本机不能用 1000 并发、千 RPS 作为未经测出的口号。

生产 HA 验证另行部署：API/Worker多副本、LB、持久层复制与备份、故障节点隔离、跨AZ恢复；本期本机只验证进程重启/局部故障。暂定 RTO/RPO 必须等备份恢复和故障实验定义并测出，不能从 Compose 自动重启推导 SLA。

## 8. 成果归档与报告模板
