## 选择与替代方案

| 问题 | 比较方案 | 本阶段决定与原因 |
| --- | --- | --- |
| MCP | 自制协议、进程 stdio、SDK Streamable HTTP | SDK + 独立 HTTP 服务，便于权限隔离、实际跨进程调用及链路测试；固定受控发布者 |
| 多工具路由 | 全量工具提示、仅 dense、权限优先混合召回 | 固定步骤精确效果路由；开放查询用授权 allowlist + 中文 BM25/dense + RRF + Top6 精排/原生函数；正式收益待成对测评 |
| 中文词法 | 自定义词典插件、CJK 内置分词 | 内置 cjk_bigram 避免额外插件供应链；在正式检索集上再判断是否值得增加词典 |
| 消息投递 | Kafka/RocketMQ、纯 Redis 队列、PG Outbox | 当前单机低规模用 PG Outbox/Inbox，事务闭环且可补偿；不把 Redis 短暂通知当可靠记录 |
| 资金幂等 | cache key、仅 checkpoint、业务账本 | 稳定 operation ID/参数 hash + 唯一约束 + 实体锁/状态机 + 权威回执；未知远端结果需要远端状态契约 |
| 审批 | 用户文本或模型布尔值、持久版本提案 | 客户确认和主管审批分离，绑定当前实体/政策/金额/revision/期限；失效必须重新确认 |
| 人工接管 | 只返回转人工文字、可领取工单 | 持久工单与接管包、领取/核对/关闭 CAS、未知副作用禁止关闭、客户可查处理结果 |
| 恢复查询 | 返回全部历史、按稳定操作定位 | 默认最近100条，精确 operation ID 查原回执，恢复不依赖截断历史列表 |

这里的“适合”受中文、现有云账号、单机资源和可验证闭环约束。没有证据支持一个框架在所有规模上“最优”。当前保留 ES、PostgreSQL/pgvector、LangGraph、AG-UI、OTel 的已审查组合；没有新增 Kafka、K8s、Istio 或重型本地模型。

## 实际兼容结果与后续判断门

v2 SDK 的 plain `dict` 返回类型、预期工具异常包装、httpx2 传输与完整 JSON schema 比对都通过实际 MCP 验证，使用 `dict[str, Any]` 返回 structured output 并保留白名单业务错误。直接 httpx2 依赖原已存在于锁文件的传递依赖中，本次没有为其升级全部依赖。

三项待正式证明的深化方向继续保持：①实体/政策证据驱动的可验证规划与局部刷新；②权限优先的分层工具检索与严格参数绑定；③稳定操作账本、故障对账及完整人工接管。记忆/AWM 的独立增益在步骤 6 实现后纳入消融。

正式结论必须遵循 [评测协议](../evaluation/benchmark-protocol.md)：同一模型、权限保护、数据和预算，冻结至少50条可执行业务黄金集，真实 Docker B0/B1/P 成对实验及消融。当前开发探针和故障测试不代替这些结果，也不证明优于 Salesforce Agentforce/Dify。
